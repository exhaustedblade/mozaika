# Архитектура (набросок, уточняется пробой в Фазе 0)

## Слои

```
┌──────────────────────── ИИ-слой (MCP) ─────────────────────────┐
│ build / change / draw / run / watch / study / verify / report  │
├─── Редактор и показ (десктоп Win/macOS · браузер · VS Code) ───┤
│ блок-схемы (React Flow) · свойства · код (Monaco) · 3D (Babylon.js) │
│ карты (MapLibre + deck.gl) · графики (ECharts) · панели        │
├──────────────────── Ядро моделирования ────────────────────────┤
│ часы и очередь событий · процессы · агенты · системная динамика│
│ пространство и пути · эксперименты · самопроверка              │
├──────────────────── Внешние движки (по желанию) ───────────────┤
│ SUMO (трафик) · JuPedSim (пешеходы) · Python (Optuna, SciPy)   │
└────────────────────────────────────────────────────────────────┘
```

Ядро не знает об отрисовке. На десктопе оно работает отдельным процессом, в браузере — в Web Worker. Ядро отдаёт снимки состояния, а показ рисует их со своей частотой. Эксперименты гоняют ядро без показа, параллельно.

## Большие популяции

Цель — сотни тысяч агентов на десктопе как норма и миллион агентов с простой логикой (П-18); главная форма продукта — настольное приложение для Windows и macOS (П-19). Отсюда правила.

- **На десктопе ядро — отдельный процесс.** Ему доступно больше памяти, чем вкладке браузера, а прогоны экспериментов (варьирование параметров, Монте-Карло) идут параллельно, по процессу на ядро процессора.
- **Снимки больших популяций — плотные числовые массивы.** Номера, состояния и движение агентов передаются typed arrays, по массиву на поле, а не JSON-объектом на каждого агента.
  - Из Web Worker массив передаётся без копирования (transferable `ArrayBuffer`). После передачи буфер принадлежит получателю, поэтому ядро пишет следующий снимок в другой буфер (двойная буферизация, ниже).
  - Видеокарта рисует такие массивы инстансингом, без перекладки.
  - Нынешние JSON-снимки (`recordSnapshots`, Ф0-2) остаются для небольших данных: статистики, графиков и панелей.
  - Снимок популяции — столбцы: номера агентов (`ids`), номер состояния по каждой параллельной области диаграммы, момент создания, отрезки движения (П-30, П-32). Устройство — ниже, в «Снимке популяции».
- **Данные в массивах, а не в объектах** (П-27, П-28). Горячий путь ядра — очередь событий, процессы, агенты — остаётся на TypeScript: код модели (действия, условия) — функции TypeScript, их вызывают на каждом событии. Скорость даёт раскладка данных: событие — запись в типизированных массивах, а не объект с замыканием. Rust или WebAssembly — только для пакетных расчётов без кода модели на каждый элемент: интерполяция движения, пространственный индекс, интегрирование больших систем СД.
- **Движение — отрезками** (П-32): откуда, куда, когда начал, когда прибудет. Прибытие — одно событие; позиции между событиями считаются формулой — пачкой в ядре и на видеокарте в показе. Устройство — [AGENTS.md](AGENTS.md), раздел 9.
- **Замер ядра (Ф0-4):**
  - 100 000 агентов с двумя состояниями (переход раз в единицу времени): 6,2 единицы модельного времени в секунду в CI (2,3–3,1 на машине разработки), 344 байта на агента;
  - миллион: около 0,14 единицы в секунду и 345 байт на агента;
  - узкое место — очередь событий, где ждёт по событию на агента: двоичная куча из объектов и промахи кэша;
  - прототип ядра на массивах (П-27): ×3–4 по скорости и около 200 байт на агента. Подробности — [AGENTS.md](AGENTS.md), раздел 6.
- **Замер ядра на массивах (Ф0-4б, П-36):** 201 байт на агента при 100 000 и 187 при миллионе (было 344–345). Скорость в CI зависит от раннера на десятки процентов, поэтому сравнение — по нескольким прогонам: 100 000 агентов — 16–27 единиц модельного времени в секунду (медиана 23) против 5,8–9,3 (медиана 6,7) у ядра из объектов, миллион — 0,82–1,20 (медиана 1,16) против 0,29–0,41 (медиана 0,31), П-36. Узкое место прежнее — спуск по куче, цепочка зависимых промахов кэша по уровням; дальше — «лестничная» очередь (П-28).
- **Замер блоков на событиях (Ф0-4в, П-41):** 100 000 сущностей одновременно в Delay — 167 байт на сущность против 663 у блоков на процессах и 3,26 → 8,01 единицы модельного времени в секунду (медианы CI, ×2,5; на разных раннерах ×2,2–4,2). Остальное время — та же куча и промахи кэша по «остывшему» агенту при уходе из блока.
- **Замер движения и снимков (Ф0-6а, П-47):** 100 000 и 1 000 000 идущих агентов — 13,5 и 1,14 единицы модельного времени в секунду (медианы CI; с движением в полях агента было 11,9 и 0,95), 291 и 257 байт на агента (было 337 и 321), снимок для показа — 0,89 и 7,6 мс (обход агентов — 2,56 и 29,9). Прежние сценарии при попеременном замере на одном раннере — в пределах ±1,2 %; память агента — 196 и 180 байт, сущности в Delay — 147 (было 201, 187 и 167).

### Снимок популяции

Реализован в Ф0-6а (`population-snapshots.ts`). Показу (Ф0-6б) нужны номера, состояния и движение всех агентов одними плотными столбцами, переданными из Web Worker без копирования.

- **Что в снимке.** `new PopulationSnapshots(population)` пишет популяцию в момент `time` в столбцы одного `ArrayBuffer`:
  - `ids` — номера (`Float64Array`), по ним показ узнаёт агента после перестановок;
  - `createdAt` — моменты создания (`Float64Array`);
  - `segments` — отрезки движения (`Float32Array`), шесть чисел на агента: откуда x, y, куда x, y, начало и прибытие **относительно момента снимка**;
  - `states` — номер состояния в области 0 (`Uint16Array`); параллельные области добавят по столбцу.

  Порядок строк — порядок столбцов популяции, длина — `size`. Столбцы идут в буфере подряд, от 8-байтных к 2-байтным, чтобы каждый был выровнен: 42 байта на агента. Один буфер — один предмет в списке передачи `postMessage` и одна запись в учёте двойной буферизации.
- **Отрезки, а не позиции** (выбор по замеру, П-44). Показ ведёт агентов между снимками сам (П-32): с отрезком позиция в любой кадр — одна формула на видеокарте, и кадры не ждут снимков ядра. Позиции в момент снимка годятся только для этого момента. Запись отрезков к тому же дешевле расчёта позиций: копия и два вычитания на агента против деления и ветвления (замер — в DECISIONS, П-44). Позиции пачкой остаются у популяции для кода модели (`population.positions()`, `Float64Array`).
- **Float32 и время относительно снимка.** Видеокарта считает во Float32. Абсолютный момент около 100 000 единиц во Float32 идёт с шагом 0,008, а разность «начало − момент снимка» у идущего агента мала, и точность у неё полная. У стоящего агента «откуда» и «куда» совпадают, поэтому неточность давнего момента начала позиции не меняет. Координаты во Float32 — около миллиметра на 10 км; модели в географических координатах сдвинут начало отсчёта (Ф0-6б).
- **Двойная буферизация.** У `PopulationSnapshots` два буфера. `take()` пишет снимок в свободный буфер и отдаёт его — буфер «одолжен». Пока его не вернули (`giveBack`), ядро в него не пишет. Если одолжены оба, `take()` возвращает `undefined`: снимок не делается, пока показ не вернёт буфер. Буфер, вернувшийся из Web Worker, — тот же кусок памяти, но новый объект `ArrayBuffer` (передача отсоединяет прежний), поэтому его принимают по номеру буфера в снимке (`slot`). Популяция выросла сверх буфера — для свободного буфера заводится больший.
- **Снимок не меняет прогон:** он только читает столбцы, событий не добавляет. Снимок в момент T — после всех событий с временем ≤ T (П-8), если его делают между `run(T)` и следующим прогоном.

### Ядро в Web Worker

Реализовано в Ф0-6а: подпуть `@mozaika/kernel/worker` — хозяин модели `KernelHost` и типы протокола. Ядро по-прежнему не знает о DOM: хозяин принимает запрос и возвращает ответ со списком буферов для передачи, а `postMessage` и `onmessage` — в тонкой обёртке на стороне показа (`packages/viewer/src/kernel-worker.ts`, несколько строк).

- **Модель — код**, поэтому в Worker её не передают, а выбирают по имени из моделей, собранных в его бандл: `new KernelHost({ walkway })`. Модель — `{ parameters, build({ seed, parameters }) }`; `build` создаёт симуляцию и называет популяции, которые показывает снимок, и, если нужно, рекордер записей для графиков (`records`). Параметры — живой объект: модель читает их в своих событиях, а запрос `set` меняет значение.
- **Протокол** (все запросы, кроме `release`, несут номер `id`, ответ повторяет его; ответы идут в порядке запросов):

  | Запрос | Что делает | Ответ |
  |---|---|---|
  | `build { model, seed?, parameters? }` | собирает модель, заводит по `PopulationSnapshots` на популяцию | `built`: время, параметры, популяции с именами состояний |
  | `run { until }` | `simulation.run(until)` | `ran`: время, число событий, причина остановки; записи модели для графиков, накопленные с прошлого ответа (`records`, если модель их ведёт, П-50) |
  | `snapshot` | снимок каждой популяции | `snapshot`: время и снимки; их буферы — в списке передачи |
  | `set { parameter, value }` | меняет параметр модели | `set`: имя и новое значение |
  | `release { snapshots }` | возвращает буферы снимков (с передачей) | — |

  Ошибка любого запроса — ответ `error` с кодом `SimulationError` и текстом: неизвестная модель или параметр — `INVALID_ARGUMENT`, прогон до сборки или снимок при одолженных буферах — `INVALID_STATE`, ошибка модели — её код (`AGENT_FAILED`, `EVENT_FAILED`…).
- **Порядок и повторяемость.** Хозяин только вызывает `run` и читает столбцы, поэтому прогон в Worker тот же, что без него: та же трасса по seed.
- **Проверка** — без настоящего Worker: тесты подают запросы прямо в `KernelHost.handle` и проверяют ответы, снимки и учёт буферов.

## Показ

Реализован в Ф0-6б (`packages/viewer`, П-48–П-52): 3D-сцена на Babylon.js, демо «пункт обслуживания» с панелью и графиками, страница замера. Показ только рисует то, что отдаёт ядро, и в прогоне ничего не меняет (П-3).

Где что: `scene/` — сцена (`Stage`), агенты (`AgentLayer`), формула шейдера и её двойник (`segment-shader.ts`), облик агентов (`agent-look.ts`), геометрия человека; `view-clock.ts`, `snapshot-feed.ts`, `live-view.ts` — часы кадров, подача снимков и цикл кадра; `models/` — модели Worker (демо и толпа замера); `demo/` и `bench/` — страницы; `e2e/` — проверки в браузере (Playwright).

**Кто где работает.**
- **Web Worker:** ядро и модель — прогон до момента кадра, снимки популяций (`PopulationSnapshots`), записи статистики для графиков (`recordSnapshots`).
- **Главный поток:** часы показа, запросы к Worker (`KernelClient`), загрузка снимка на видеокарту, вызов отрисовки, панель и графики. Позиции агентов на CPU не считаются.
- **Видеокарта:** позиция и цвет каждого агента — в вершинном шейдере.

**Часы и частоты.**
- Кадры — `requestAnimationFrame`, обычно 60 в секунду. Модельное время кадра `t` растёт со скоростью из панели (единиц модельного времени в секунду реального).
- Снимок: показ шлёт парой `run { until: t }` и `snapshot`. Следующую пару — когда пришёл ответ на предыдущую, но не чаще 20 раз в секунду. Чаще не нужно: между снимками агенты идут по своим отрезкам сами, а каждый снимок — загрузка на видеокарту (30 байт на агента, 3 МБ на 100 000).
- Кадр рисует последний снимок (момент `T ≤ t`): агент идёт по отрезку из снимка, пока следующий снимок не принесёт новый. Новый маршрут показ видит с задержкой не больше интервала снимков и пути ответа — десятки миллисекунд реального времени.
- Ядро не успевает за часами — часы ждут его: `t` уходит от последнего снимка не дальше, чем на 0,25 с реального времени. Иначе агенты, дошедшие до цели, стояли бы, пока ядро не выдаст им новые отрезки.

**Инстансинг.** Все агенты популяции рисуются одним вызовом: геометрия одного агента (низкополигональный человек) и атрибуты экземпляров прямо из столбцов снимка, без перекладки на CPU:
- `segments` (`Float32`, шесть чисел, 24 байта на агента) — один буфер с шагом 24 байта и два атрибута в нём: `fromTo` (vec4: откуда x, y, куда x, y) со смещением 0 и `times` (vec2: начало и прибытие от момента снимка) со смещением 16;
- `states` (`Uint16`) — атрибут `state`; цвет — из таблицы цветов состояний (uniform), её задаёт показ модели;
- `ids` (`Float64`) — для сопоставления агентов между снимками. Строки снимка меняются при удалениях (на место удалённого встаёт последний, П-30), поэтому всё, что показ связывает с агентом дольше одного снимка, — облик, выбранный агент, подпись — привязано к номеру, а не к строке. В Ф0-6б по номеру считается облик: оттенок и рост чуть различаются у разных людей и не меняются, когда агент переезжает в другую строку. На видеокарту номер идёт атрибутом `agentId` во `Float32`: точен до 2²⁴ (16,7 млн), дальше облики повторяются, что для облика неважно;
- `createdAt` показу пока не нужен.

Буферы на видеокарте — с запасом, ёмкость — степень двойки, как у снимков; растут вместе с популяцией. Снимок загружается одной записью на буфер и сразу возвращается ядру (`release`): данные уже на видеокарте, поэтому буфер снимка занят только на время загрузки, и двойная буферизация не ждёт отрисовки. Загрузка называет число агентов, поэтому Babylon.js не хранит ссылку на память снимка; потерянный контекст WebGL возвращается с пустыми буферами той же ёмкости, и агенты не рисуются до следующего снимка.

**Позиция в шейдере.** Главный поток считает `since = t − T` во `Float64` и передаёт uniform во `Float32`: число маленькое, точность полная. Шейдер ведёт агента по формуле отрезка (AGENTS.md, раздел 9) — той же, что у ядра и у `positionsAt` в 2D-проверке:

```glsl
vec2 segmentPosition(vec4 fromTo, vec2 times, float since) {
  if (since >= times.y) return fromTo.zw;  // с момента прибытия — ровно «куда»
  if (since <= times.x) return fromTo.xy;  // до начала отрезка — «откуда»
  return fromTo.xy + (fromTo.zw - fromTo.xy) * ((since - times.x) / (times.y - times.x));
}
```

Вторая ветка даёт то же, что `max(0, k)` у `positionsAt`, и избавляет от деления на ноль у отрезка нулевой длительности. Проверка: двойник формулы на TypeScript (по шагам во `Float32`) сверяется тестами с `positionsAt` и с позициями ядра, а сам шейдер на видеокарте — тестом Playwright через transform feedback.

**Координаты во Float32.** Отрезки в снимке — `Float32` в единицах длины модели: около миллиметра на 10 км от начала координат. Поэтому модель держит координаты площадки в метрах вокруг своего начала отсчёта (центр или угол площадки). Модель в географических координатах переводит их в метры от выбранной точки; сама точка отсчёта — `Float64` на CPU, для карт (Фаза 2), на видеокарту она не идёт. Время в шейдере — тоже разность (`since`, начало и прибытие от момента снимка), поэтому абсолютный момент около 100 000 единиц точности не съедает. Плоскость модели `x, y` — пол сцены: `x` направо, `y` вглубь сцены; высоты в модели нет (П-43), агенты стоят на полу.

**Графики и панель.** Статистика остаётся в Worker, вместе с моделью. Данные графиков — записи `recordSnapshots` модели: статистика через равные промежутки модельного времени (`start + k·every`), а не в моменты запросов показа. Поэтому записи не зависят от частоты кадров и скорости машины: при том же seed графики те же. Модель отдаёт рекордер хозяину (`WorkerModel.records`), а ответ `ran` приносит записи, накопленные с прошлого ответа. Новый запрос протокола не нужен: записи — побочный продукт прогона и идут с его ответом, без лишнего обмена. Панель меняет параметры запросом `set`, модель читает их в своих событиях. Параметр, который меняет устройство модели (например, число окон — ёмкость пула задаётся при создании), применяется пересборкой модели с тем же seed.

**Выбор движка** — по замеру (П-48): один и тот же сценарий на Babylon.js и three.js. Кадры одинаковы по устройству (один вызов, один шейдер); на 100 000 работа главного потока равна; на миллионе Babylon.js грузит снимок прямо из буфера ядра вне кадра (кадр 1,2 мс против 8–23 мс у three.js, где снимок копируется и отправляется внутри кадра); WebGPU, PBR, тени, glTF — из коробки, API по semver. Цена — бандл вдвое больше (328 КБ gzip против 168 КБ). Babylon.js рисует в правосторонней сцене с осью y вверх, как у формул выше; свои меши обходятся против часовой стрелки, и материалам это задано явно.

**Демо «пункт обслуживания»** (П-51): Source → Queue → Service (ResourcePool «окна») → Sink на блоках; люди ходят действиями блоков `onEnter` и `onExit`. Панель меняет поток и время обслуживания запросом `set`, число окон — пересборкой. Графики (ECharts) — длина очереди, загрузка окон и время в системе, за последнюю минуту и в среднем с начала; самопроверка — законы модели на каждой записи (баланс, закон Литтла на траектории, загрузка).

**Замер показа** — страница `bench.html` (П-52): 100 000 идущих агентов (и миллион для сведения), кадры в секунду, интервал и работа кадра в главном потоке, время снимка и прогона в Worker, загрузка снимка. Время обработки запроса меряет обёртка Worker (`worker-answer.ts`): ядро системных часов не читает. В CI (job Scene) видеокарта программная, и кадры там — ориентир; цель П-18 проверяется на компьютерах владельца.

## Ядро времени

Реализовано в `packages/kernel` (Ф0-2). Ядро не зависит от DOM и Node, не читает системные часы и ничего не рисует: прогон зависит только от модели и seed.

- **Время** — число (double) в единицах модели (минуты, часы — решает модель). Начинается со `startTime` (по умолчанию 0) и только растёт: часы переходят от события к событию. События одновременны, только если их времена в точности равны. Поэтому моменты, которые должны совпасть, считаются одинаково или шагом, точным в двоичной записи (0,25, а не 0,1).
- **Очередь событий** (Ф0-4б, П-28, П-34) — записи в типизированных массивах, без объекта и замыкания на событие. Устройство — ниже, в «Очереди событий на массивах».
- **Правило одновременных событий:**
  1. раньше время — раньше событие;
  2. при равном времени раньше меньший приоритет: по умолчанию 0, отрицательные раньше, положительные позже;
  3. при равных времени и приоритете раньше то, что раньше поставлено в очередь: порядковый номер растёт с каждой постановкой.

  Номер уникален, поэтому порядок полный и не зависит от устройства кучи. Следствия:
  - событие с задержкой 0 срабатывает в тот же момент, но после событий того же момента и приоритета, уже стоящих в очереди;
  - процесс стартует не внутри `sim.process()`, а отдельным событием в текущий момент;
  - сигнал будит ожидающих в том порядке, в котором они начали ждать; каждое пробуждение — новое событие в текущий момент;
  - снимок состояния в момент T делается после всех событий с временем ≤ T.
- **Прогон:**
  - `run(until)` — события до момента `until` включительно, после чего часы стоят на `until`;
  - `run()` — до пустой очереди;
  - `step()` — одно событие;
  - `stop()` изнутри события — выход из `run()` после этого события.

  Прогон по кускам даёт то же, что прогон целиком. Отменённое событие (`handle.cancel()`) сразу удаляется из очереди.
- **Процессы** — генераторы TypeScript, как в SimPy: `yield timeout(dt)`, `const value = yield signal.wait()`. Процесс может запустить другой (`sim.process(...)`); то, что вернул генератор, — `process.result`. Набор команд закрыт; составные ожидания, например захват ресурса в Ф0-3, — обычные генераторы, их подключают через `yield*`: `yield* pool.seize()`.
- **Сигналы:** `signal.notify(value)` будит всех, кто ждёт в этот момент. Кто начал ждать позже, ждёт следующего уведомления; уведомление, которого никто не ждал, не запоминается. Кроме процессов, сигнала может ждать обычная функция (`signal.once`) — это пригодится диаграммам состояний (Ф0-4).
- **Агенты** — см. раздел «Агенты» ниже: поля и диаграммы состояний на своём лёгком исполнителе, определения в форме XState.
- **Системная динамика:** запасы, потоки, переменные. Интегрирование Эйлером или RK4 с шагом dt как периодическое событие ядра. Пересечение порога внутри шага: событие ставится в момент пересечения (линейная интерполяция). Это нужно, чтобы агенты реагировали вовремя.
- **Случайность:**
  - генератор xoshiro128\*\* — свой код без зависимостей; состояние выводится из seed и пути имён потока через SplitMix64;
  - у каждого источника случайности свой поток: `sim.random.stream('arrivals')`. Поток не зависит от порядка создания и от того, сколько чисел взяли другие потоки, поэтому правка одной части модели не сдвигает случайные числа остальных;
  - повтор эксперимента номер k — свой поток: `new Random(seed, ['replication', String(k)])`;
  - распределения: равномерное и экспоненциальное (параметр — среднее);
  - одинаковый seed даёт одинаковую трассу событий в одном движке JavaScript.
- **Снимки состояния:** `sim.recordSnapshots({ every, capture })`. Ядро вызывает функцию модели `capture(time)` в моменты `start + k·every`, пока часы стоят на этом моменте, и копит результат. Это простые данные (тип `JsonValue`), которые переживают JSON и `postMessage`. Снимки не добавляют событий и не меняют прогон. `recorder.take()` отдаёт накопленное — для статистики, графиков и панелей. Столбцы больших популяций идут отдельно: `PopulationSnapshots` (раздел «Снимок популяции»).
- **Ошибки** — `SimulationError` с кодом, чтобы ИИ-слой и viewer реагировали на ошибку и переводили сообщение, не разбирая текст:
  - `NEGATIVE_DELAY`, `EVENT_IN_PAST`, `NOT_A_NUMBER`, `NOT_FINITE`, `INVALID_ARGUMENT`, `INVALID_YIELD`, `REENTRANT_CALL`;
  - `INVALID_STATE` — действие не подходит к состоянию модели: освобождение незахваченной единицы ресурса, уход сущности из несоединённого блока, зациклившиеся условия агента. Его поднимают блоки (Ф0-3) и агенты (Ф0-4);
  - ошибка внутри события, процесса или шага агента оборачивается в `EVENT_FAILED`, `PROCESS_FAILED` или `AGENT_FAILED`: с именем, моментом времени и исходной ошибкой в `cause`.
- **Трасса:** параметр `trace` получает каждое событие перед срабатыванием (время, приоритет, номер, имя). Нужна для отладки, тестов повторяемости и консоли инструмента `run`.
- **Блоки** — процессные блоки поверх ядра, см. раздел «Блоки процессов». Сущность в блоках — агент (Ф0-4в): он идёт по блокам и одновременно живёт по диаграмме состояний; читать переменные системной динамики он сможет с Ф0-5.

### Очередь событий на массивах

Реализована в Ф0-4б (П-28, П-34): `event-records.ts`, `four-ary-heap.ts`, `scheduler.ts`. Публичный API (`schedule`, `scheduleAt`, `EventHandle`, `trace`, `run`, `step`, `stop`) прежний.

- **Запись события** занимает слот — номер строки в столбцах типизированных массивов:
  - в записях (`EventRecords`): приоритет и порядковый номер — `Float64Array`, вид — `Uint16Array`, получатель и данные — `Int32Array`, поколение слота — `Uint32Array`;
  - время — в самой куче, рядом с номером слота: сравнения почти всегда решаются по времени и так читают соседние ячейки памяти;
  - около 50 байт на ожидающее событие вместо объекта события, замыкания и указателя в куче.
- **Виды событий.** Вид — номер обработчика в таблице видов симуляции. Обработчик срабатывает по паре (получатель, данные) и по ней же называет событие:
  - функция модели (`schedule`, `scheduleAt`): данные — строка таблицы функций модели (функция и метка);
  - пробуждение процесса или слушателя сигнала (`timeout`, `signal.wait()`, `signal.once`): данные — строка таблицы пробуждений (функция продолжения, созданная один раз на процесс, значение сигнала, метка);
  - таймаут агента: получатель — место агента в столбцах популяции, данные — номер таймера диаграммы;
  - сообщение агента: данные — строка таблицы сообщений популяции (агент и сообщение).

  Первые два вида ядро регистрирует само, популяция — по два своих (таймауты и сообщения), а пакеты поверх ядра — свои через API расширения (ниже; блоки — по виду на блок и на пул). Таблицы — обычные массивы со списком свободных строк; они растут по числу ожидающих событий своего вида, а не всей очереди. Таймауты агентов таблиц не требуют. Ошибку события называет его обработчик: `EVENT_FAILED` — с меткой, `PROCESS_FAILED` и `AGENT_FAILED` — с именем процесса или агента.
- **API расширения** (`@mozaika/kernel/extension`, П-37) — для пакетов, которые строят библиотеки поверх ядра, сейчас для блоков. Внутренний `Scheduler` по-прежнему закрыт: пакет получает только свой вид событий.
  - `new EventKind(simulation, handler)` регистрирует вид; `handler` — объект с `fire(target, data)` и `label(target, data)`;
  - `kind.schedule(delay, target, data)` ставит событие этого вида на «сейчас + delay» с приоритетом 0. Задержка проверяется, как в `schedule()` (конечная, неотрицательная), `target` и `data` — целые 32-битные числа;
  - срабатывает событие только у своего обработчика; что бросил `fire`, ядро оборачивает в `EVENT_FAILED` с меткой события;
  - отмены, доступа к очереди, к чужим событиям и к часам нет. Поэтому код, который им пользуется, не может нарушить правило П-8, поставить событие в прошлое или тронуть чужие события, — он только не платит объектом и замыканием за событие. Модуль не входит в главный экспорт `@mozaika/kernel`: код модели ставит события через `schedule()`.
- **Слоты и поколения.** Слот освобождается, когда событие сработало или отменено: его поколение растёт на единицу, а сам он уходит в стек свободных и выдаётся первым — его строки ещё в кэше. `EventHandle` помнит слот и поколение: `pending` — поколение то же; `cancel()` у старой ручки после переиспользования слота ничего не делает и чужое событие не трогает.
- **Куча** — индексированная 4-арная (`FourAryHeap`):
  - массивы времени и слотов в порядке кучи и позиция каждого слота в куче; дети узла i — 4i+1…4i+4, их времена лежат рядом;
  - при равных временах сравниваются приоритет, затем номер из записей;
  - вершина удаляется «снизу вверх»: дыра спускается к листу по меньшим детям, затем в неё поднимается последний элемент. Последний обычно поздний, ему место внизу, поэтому сравнений меньше. На прототипе это быстрее обычного спуска на 1 000 и 1 000 000 событий и не медленнее на 100 000;
  - отмена удаляет событие сразу: по позиции слота на его место встаёт последний элемент и поднимается или опускается. Память ограничена числом ожидающих событий.
- **Очередь за интерфейсом** `EventQueue` (добавить, удалить, время первого, снять первое). Записи, виды и обработчики от него не зависят, поэтому кучу можно заменить «лестничной» очередью (ladder queue), если на миллионе агентов понадобится скорость.
- **Почему порядок П-8 не меняется.** Ключ (время, приоритет, номер) — строгий полный порядок: номер уникален. Куча снимает минимум по ключу, поэтому порядок срабатывания задаёт ключ, а не устройство очереди. Номера выдаёт тот же счётчик, по одному на каждую постановку — `schedule`, старт и пробуждение процесса, таймер и сообщение агента — в прежнем порядке, поэтому номера в трассе прежние.
- **Метки** событий считаются только для трассы и ошибок — из вида, получателя и данных (П-29). Пока трассы нет, строк на событие не создаётся.
- **Снимок** перед событием делается, пока событие ещё в очереди: `pendingEvents` в `capture` учитывает его (до Ф0-4б событие уже было вынуто). Состояние модели в снимке то же.

## Блоки процессов

Реализованы в `packages/blocks`: Source, Queue, Service, Delay, Sink, ResourcePool, действия при входе и выходе и статистика. Поведение каждого блока — в [BLOCKS.md](BLOCKS.md). С Ф0-4в (П-31, П-37–П-40) блоки работают на событиях ядра, а сущность — агент популяции.

- **Сущность — агент** (П-38). Source по умолчанию создаёт агентов своей популяции: имя — имя источника, диаграмма `entity` из одного состояния `active`, без полей (все агенты делят один пустой замороженный `context`). Фабрика `entity` (П-25) возвращает агента любой популяции. Номер сущности — номер прихода в симуляции, как и раньше: источник передаёт его в `population.add(undefined, { id })`. Sink удаляет агента из популяции (`population.remove`). Поэтому все движущиеся объекты — в плотных столбцах популяций (`ids()`, `stateCodes()`), откуда их возьмёт показ (Ф0-6).
- **Без процесса на сущность** (П-39). Блок держит свои сущности в таблице: строка — агент и момент входа (для времени ожидания). Каждый Source, Service, Delay и каждый ResourcePool регистрирует свой вид событий через API расширения ядра; событие несёт строку сущности. События:
  - Source — старт и приходы;
  - Service — конец обслуживания;
  - Delay — конец задержки;
  - ResourcePool — выдача единицы запросу блока, который ждал её или стоял за выданными раньше (места блока — тоже ResourcePool).

  Queue и Sink своих событий не имеют: сущность входит и уходит внутри чужих событий.
- **Движение.** Блок, в который можно войти, реализует `EntityReceiver`: `tryReserve(requester, ticket)` и `reserve(requester, ticket)` отвечают `'granted'`, `'pending'` или (только `tryReserve`) `'refused'`; `enter(agent)` — вход в блок, где у сущности уже есть место. Готовая уйти сущность просит место у следующего блока, передавая свой блок и свою строку. `'granted'` — уходит сразу, в том же событии, и входит в следующий блок; `'pending'` — ждёт, а пул мест следующего блока позже вызовет `requester.unitGranted(pool, ticket)` в своём событии выдачи. Так сущность за одно событие проходит все блоки, где ждать не нужно.
- **ResourcePool (П-15)** — счётчик занятых единиц, очередь запросов FIFO и число выданных, но ещё не продолживших запросов. В очереди вперемешку стоят запросы блоков (блок и номер строки, без объекта на запрос) и процессов модели (`yield* pool.seize()`, сигнал на ожидание, как раньше). Освобождённая единица сразу передаётся первому в очереди: процессу — пробуждением по сигналу, блоку — событием выдачи; оба ставятся в момент передачи, поэтому продолжают в порядке выдачи. Запрос при свободной единице, но при выданных и не продолживших, продолжает событием после них. Места блоков (П-14) — такой же пул внутри блока.
- **Порядок одновременных событий** не зависит от устройства: все решения о выдаче принимаются в момент освобождения по очереди FIFO, события блоков — обычные события ядра с приоритетом 0 и правилом П-8. Отличие от блоков на процессах одно: сущность входит в первый блок в событии прихода, а не в событии старта своего процесса чуть позже. Место в первом блоке и раньше занималось в событии прихода, а единицы выдаются по тем же правилам; отпечатки итогов двух потоков с множеством одновременных событий совпадают с блоками на процессах (BLOCKS.md, раздел 10).
- **Действия при входе и выходе** (П-40): `onEnter` и `onExit` получают `{ agent, block, now }` и выполняются внутри события блока — `onEnter` после учёта входа, `onExit` до учёта ухода.
- **Соединение:** у блока один выход, `source.connect(service).connect(sink)`.
- **Статистика:** `TimeAverage` — среднее по времени вплоть до текущего момента, его можно читать и в снимке; `Tally` — число и среднее наблюдений. `resetStatistics()` у блоков и пула отбрасывает разгон.
- **Имена и потоки (П-13):** имя блока уникально в симуляции, поток случайных чисел блока — `blocks/<имя>`, номера сущностей идут по порядку приходов. Эти данные пакет хранит в `WeakMap` по симуляции и читает при создании блока, а не на каждую сущность: ядро о блоках не знает.
- **Что добавлено в ядро:** в Ф0-3 — код ошибки `INVALID_STATE`; в Ф0-4в — API расширения `@mozaika/kernel/extension` (вид событий для пакета) и номер агента при создании (`population.add(fields, { id })`).
- **Проверка:** детерминированные тесты порядка событий, FIFO и вместимости; закон Литтла точно на одной траектории; сверка M/M/1, M/M/c и M/M/1/K с формулами по 20 повторам (П-16); пул, общий для блоков и процесса модели; агент через все блоки и удаление в Sink; действия; отпечатки итогов, совпадающие с блоками на процессах, и отпечаток новой трассы; замер M/M/1 и 100 000 сущностей в Delay в `pnpm bench` (П-17, П-41).

## Агенты

Реализованы в `packages/kernel/src/agents` (Ф0-4) — модуль ядра, а не отдельный пакет (П-20). Поведение — в [AGENTS.md](AGENTS.md).

- **Тип агента** — диаграмма состояний `defineStatechart(config, { delays })`: подмножество машины XState v5 по форме, без зависимости от XState (П-21). Определение проверяется и компилируется один раз (`compile.ts`): переходы ссылаются прямо на целевые состояния, таймеры пронумерованы.
- **Популяция** (`AgentPopulation`, `store.ts`) — агенты одного типа и их плотные столбцы (П-30, П-35): номер и момент создания рядом, по два `Float64` на строку (момент создания — с Ф0-6а), номер состояния по области диаграммы (`Uint16Array`, пока область одна), слоты ожидающих таймаутов (`Int32Array`), счётчики по состояниям; у популяции, чьи агенты двигались, — ещё отрезки движения (`motion.ts`). `ids()`, `stateCodes(region)` и `positions()` — копии столбцов; снимок для показа — `PopulationSnapshots` (раздел «Снимок популяции»). `remove(agent)` отменяет таймауты и прибытие агента и ставит на его строку последнего агента.
- **Движение** (Ф0-6а, П-32, П-43) — [AGENTS.md](AGENTS.md), раздел 9: `agent.placeAt(point)`, `agent.moveTo(point, { speed | duration, stopOnExit? })`, `agent.stop()`, `agent.position`, `agent.moving`, `population.positions()`. Отрезок — шесть `Float64` в строке движения агента (64 байта вместе со слотом прибытия и признаком `stopOnExit`, одна строка кэша); прибытие — одно событие третьего вида популяции, на него агент делает шаг со служебным событием `{ type: 'agent.arrived' }` и переходом `on['agent.arrived']`. Новое движение, остановка, выход из состояния (если движение к нему привязано, `stopOnExit`) и удаление отменяют прибытие.
- **Агент — не процесс.** Таймауты и сообщения — события двух видов, которые регистрирует популяция (П-34): таймаут несёт строку агента и номер таймера, сообщение — строку таблицы сообщений популяции (агент и сообщение). Таймаут отменяется при выходе из состояния по слоту из столбца. Агент стартует синхронно внутри `add()`. Шаг агента: переход по событию, затем переходы по условиям до устойчивого состояния, всё в один момент (П-24). Метки событий называют агента и считаются только для трассы и ошибок (П-29).
- **Условия** проверяются после входа в состояние, после каждого события агента и по `check()`; опроса по шагу нет (П-22).
- **Случайность:** поток `agents/<популяция>` для действий и `agents/<популяция>/<задержка>` для каждой задержки-функции; потока на агента нет — он дорог (П-23).
- **Агент как сущность:** всё, что движется по блокам, — агент (П-31, П-38). Source создаёт агентов своей популяции или фабрикой `entity` (П-25), Sink удаляет их из популяции. Номер агента можно задать при создании: `population.add(fields, { id })` — больше всех прежних номеров популяции; так источник даёт сущности номер прихода.
- **Что добавлено в ядро:** в Ф0-4 — модуль `agents`, код ошибки `AGENT_FAILED` (его, как и `PROCESS_FAILED`, ядро не оборачивает в `EVENT_FAILED`) и экспорт `@mozaika/kernel/test-support` — помощники тестов всех пакетов, только в исходниках рабочего пространства, не в сборке. В Ф0-4б — очередь на массивах с видами событий (раздел «Очередь событий на массивах»); публичный API ядра прежний, у популяции добавились `remove`, `ids`, `stateCodes(region)`, у агента — `removed`, у диаграммы — `regionCount`. В Ф0-4в — номер агента при создании (`add(fields, { id })`) и API расширения для блоков. В Ф0-6а — движение (у агента `position`, `moving`, `placeAt`, `moveTo`, `stop`, у популяции `positions()`, типы `Point` и `MoveOptions`), снимок популяции `PopulationSnapshots` и подпуть `@mozaika/kernel/worker`; `agent.createdAt` читается из столбца популяции, у удалённого агента его больше нет (П-46).
- **Проверка:** моменты переходов, повторяемость трассы, удаление агентов, агент в очереди на блоках, аналитическая проверка N агентов с двумя состояниями по 20 повторам (П-16); движение (позиция по формуле, одно прибытие, отмены), снимки и двойная буферизация, протокол Worker; замер 100 000 и 1 000 000 агентов, неподвижных и движущихся, в `pnpm bench` (П-26, П-36). Трассы модели процессов, модели агентов и потока блоков совпадают событие в событие (с номерами) с ядром Ф0-4 — отпечатки трасс записаны в тестах.

## Формат модели — текст, удобный для git

```
model/
  model.json         — метаданные, единицы времени, параметры, эксперименты
  agents/*.ts        — типы агентов: поля, диаграммы состояний, функции
  flows/*.json       — блок-схемы процессов (узлы, порты, связи, свойства)
  sd/*.json|.xmile   — системная динамика
  scene/*.json       — 2D/3D-сцена, камеры, панели
  data/*             — таблицы (CSV, Excel, DuckDB)
  tests/*.ts         — законы модели для самопроверки
```

Каждая правка — это маленький понятный diff. ИИ и человек правят одно и то же.

## ИИ-инструменты (перенос словаря Architect)

| Инструмент | Что делает |
|---|---|
| `status`, `map`, `read` | что есть в модели |
| `change` | операции над моделью (создать, изменить, связать, удалить) |
| `draw` | сцена скриптом (2D/3D), перерисовка по разнице |
| `build` | проверка модели: типы, связи, единицы |
| `run` | прогон с KPI, консоль, ошибки |
| `watch` | кадры показа в заданные моменты |
| `study` | Монте-Карло, чувствительность, оптимизация, калибровка |
| `verify` | самопроверка, независимый пересчёт, устойчивость |
| `report` | отчёт и гайд по модели |

## Проверка как часть продукта

- **Законы модели** (`tests/`) — балансы, границы, монотонность, сложение сценариев. Запускаются кнопкой и в CI.
- **Мутационная проверка законов:** намеренная порча, и закон должен поймать её.
- **Для индексов** — анализ устойчивости по методике OECD/JRC (корреляции, веса, нормирование, чувствительность).
