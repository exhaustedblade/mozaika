# Агенты и диаграммы состояний: спецификация поведения

Спецификация для Ф0-4: тип агента с полями и диаграммой состояний, переходы по таймауту, интенсивности, сообщению и условию, агент как сущность процессных блоков. В Ф0-4б добавлены удаление агентов и столбцы популяции (П-30). Код в `packages/kernel/src/agents` написан по ней.

**Источники** (правила «чистой комнаты», [LEGAL.md](LEGAL.md)): открытые статьи, стандарты и документация. Закрытые программы не использовались.

- D. Harel. *Statecharts: A Visual Formalism for Complex Systems*. Science of Computer Programming 8, 1987 — диаграммы состояний, действия при входе и выходе, переходы по событию и условию.
- OMG. *Unified Modeling Language*, версия 2.5.1, 2017, глава 14 «State Machines» — порядок действий при переходе (выход, действия перехода, вход), события-изменения и таймеры, отбрасывание событий без перехода.
- W3C. *State Chart XML (SCXML)*, рекомендация 2015 — шаги и микрошаги, переходы без события (eventless) проверяются после каждого шага, порядок переходов «как в документе».
- Документация XState v5 (stately.ai/docs, MIT) — форма определения: `initial`, `context`, `states`, `on`, `after`, `always`, `entry`, `exit`, `guard`, `actions`, `reenter`, `type: 'final'`. Сама библиотека XState не подключается.
- S. M. Ross. *Introduction to Probability Models*, 12-е изд., 2019, гл. 6 — марковская цепь с двумя состояниями и непрерывным временем (аналитическая проверка, раздел 10).

## 1. Понятия

**Диаграмма состояний** (`defineStatechart`) описывает тип агента: его поля, состояния и переходы. Одна диаграмма может служить нескольким популяциям.

**Популяция** (`AgentPopulation`) — все агенты одного типа в симуляции: диаграмма, имя и общие данные агентов. Имя популяции обязательно и уникально в симуляции: по нему выбираются потоки случайных чисел (раздел 7). Агентов добавляет `add()`, удаляет `remove()` (раздел 3).

**Агент** (`Agent`) — один экземпляр типа:
- `id` — номер в популяции: 1, 2, 3… по порядку создания; номер удалённого агента не переиспользуется;
- `createdAt` — момент создания;
- `context` — поля агента (объект, у каждого агента свой);
- `state` — имя текущего состояния;
- `done` — агент дошёл до конечного состояния (раздел 3);
- `removed` — агент удалён из популяции (раздел 3).

**Состояния** в этой версии плоские: обычные и конечные. Вложенные (иерархические) и параллельные состояния, история — позже; определение с ними отклоняется с ошибкой (раздел 9).

## 2. Формат определения

Определение — объект той же формы, что машина XState v5, и ограниченный набор ключей из неё (решение П-21). Время задержек — в единицах модельного времени (в XState — миллисекунды).

```ts
const customer = defineStatechart(
  {
    id: 'customer',
    initial: 'waiting',
    context: { patience: 2.5, complaints: 0 },
    states: {
      waiting: {
        after: { patience: 'impatient' },             // таймаут: именованная задержка
        on: { called: 'served' },                     // сообщение
      },
      impatient: {
        entry: ({ context }) => { context.complaints++; },
        on: { called: 'served', apology: { target: 'waiting', reenter: true } },
        always: { guard: ({ context }) => context.complaints > 3, target: 'gone' }, // условие
      },
      served: { type: 'final' },
      gone: { type: 'final' },
    },
  },
  {
    delays: {
      patience: ({ context }) => context.patience,    // задержка из поля
      // или patience: rate(0.5) — экспоненциальная задержка с интенсивностью 0,5
    },
  },
);
const customers = new AgentPopulation(sim, { name: 'customers', statechart: customer });
const agent = customers.add({ patience: 4 });
agent.send({ type: 'called' });
```

**Ключи определения:**

| Где | Ключ | Что значит |
|---|---|---|
| диаграмма | `initial` | имя начального состояния, обязательно |
| | `states` | состояния: имя → описание, хотя бы одно |
| | `context` | начальные поля: объект (каждый агент получает свою поверхностную копию) или функция `({ id, now, random }) => поля` — для вложенных объектов и случайных начальных значений |
| | `id`, `description` | имя и описание, только для чтения людьми и инструментами |
| состояние | `type` | `'atomic'` (по умолчанию) или `'final'` — конечное |
| | `entry`, `exit` | действие или массив действий при входе и выходе |
| | `on` | переходы по сообщениям: тип сообщения → переход(ы) |
| | `after` | переходы по таймауту: задержка → переход(ы); задержка — число или имя из `delays` |
| | `always` | переходы по условию (без события) |
| | `description` | описание |
| переход | строка | короткая запись перехода в состояние с этим именем |
| | `target` | целевое состояние; без него переход только выполняет действия |
| | `guard` | условие: функция → `true`/`false` |
| | `actions` | действие или массив действий |
| | `reenter` | `true` — выйти из состояния и войти заново, даже если цель — оно само |
| | `description` | описание |

Где допускается «переход(ы)», можно дать массив: переходы пробуются по порядку, срабатывает первый, чьё условие истинно (или у которого условия нет).

**Второй аргумент** `defineStatechart` — реализации: `delays` — именованные задержки, число или функция. Так же задержки передаются в XState (`setup({ delays })` в v5, второй аргумент `createMachine` в v4).

**Аргументы функций.** Действия, условия и задержки получают один объект:
- `agent` — сам агент;
- `context` — его поля (тот же объект, что `agent.context`);
- `event` — событие шага: сообщение или служебное событие `{ type: 'agent.start' }` (создание), `{ type: 'agent.after', delay }` (таймаут), `{ type: 'agent.check' }` (явная проверка условий);
- `now` — модельное время;
- `random` — поток случайных чисел: у функции задержки — поток этой задержки, у остальных — поток популяции (раздел 7).

**Отличия от XState** — сознательные, ради скорости и простоты:
- поля меняются прямо в действии (`context.x = 1`), без `assign`: у 100 000 агентов копировать поля на каждое изменение дорого;
- условия, действия и функции задержек — только функции в самом определении (inline); строковые имена условий и действий, `assign`, `raise`, `sendTo`, `invoke`, `tags`, `meta` не поддерживаются;
- неизвестный ключ — ошибка с перечнем поддерживаемых: опечатка (`afetr`) не должна тихо выключать переход.

## 3. Жизнь агента

**Создание** — `population.add(fields?)`:
1. поля: копия `context` или результат функции `context`, поверх — `fields`;
2. агент добавляется в популяцию и **сразу**, внутри вызова `add()`, входит в начальное состояние. Отдельного события на старт нет: при 100 000 агентов это 100 000 лишних событий. Этим агент отличается от процесса ядра, который стартует событием (П-8).

**Вход в состояние** — по шагам:
1. состояние становится текущим (`agent.state`, счётчики популяции);
2. действия `entry` по порядку;
3. запускаются таймеры `after` (раздел 4.1) — после `entry`, поэтому задержка может зависеть от полей, заданных при входе;
4. если состояние конечное, агент завершён: `done = true`, таймеров и проверок условий больше нет, сообщения отбрасываются;
5. проверяются условия `always` (раздел 4.4).

**Выход из состояния:** отменяются все его таймеры, затем действия `exit`.

**Переход** (UML, SCXML и XState одинаково): выход из исходного состояния → действия перехода → вход в целевое. Во время `exit` и действий перехода `agent.state` — ещё исходное состояние, во время `entry` — уже целевое.

- **Переход без цели** только выполняет действия: выхода и входа нет, таймеры идут дальше.
- **Переход в то же состояние** без `reenter` — как в XState v5: выхода и входа нет, таймеры идут дальше, выполняются только действия перехода. С `reenter: true` агент выходит и входит заново: `exit`, `entry`, таймеры запускаются заново. В UML и SCXML по умолчанию наоборот (внешний переход); выбран XState v5, чтобы одно и то же определение вело себя одинаково здесь и в XState.

**Конечное состояние** (`type: 'final'`) не имеет переходов, таймеров и `exit`; `entry` допустим. Агент в конечном состоянии остаётся в популяции и учитывается в её счётчиках, пока его не удалят.

**Удаление** — `population.remove(agent)` (решения П-30, П-35):
1. таймеры агента отменяются — их события уходят из очереди сразу;
2. агент уходит из счётчиков, а его строку в столбцах популяции занимает последний агент (столбцы остаются плотными, раздел 6). Поэтому `population.agents`, `ids()` и `stateCodes()` идут в порядке создания только до первого удаления;
3. сообщения, которые уже в пути к удалённому агенту или посланы ему потом, отбрасываются при доставке и считаются в `population.discardedMessages`;
4. удалённый агент сохраняет `id`, `createdAt`, поля и последнее состояние (`state`, `done`), `removed = true`; ни на что больше не реагирует, `check()` ничего не делает.

Агент, который удаляет сам себя из своего действия (например, при входе в конечное состояние «ушёл»), уходит в конце своего шага: шаг доходит до конца, затем срабатывает удаление. Повторное удаление возвращает `false`, агент чужой популяции или не агент — ошибка `INVALID_ARGUMENT`.

## 4. Переходы

### 4.1. По таймауту

`after: { 5: 'B' }` или `after: { patience: 'B' }` с `delays: { patience: … }`.

- Задержка вычисляется при входе в состояние; таймер — событие ядра в момент «вход + задержка».
- Задержка — конечное неотрицательное число или `Infinity` («никогда»: таймер не ставится). Отрицательная задержка или `NaN` — ошибка.
- **При выходе из состояния таймер отменяется** (`handle.cancel()`): переход по нему уже не сработает, событие не попадает в прогон.
- Когда таймер срабатывает, проверяются условия его переходов; если ни одно не истинно, ничего не происходит, таймер израсходован (в этом посещении состояния он больше не сработает).

### 4.2. По интенсивности

Переход «с интенсивностью λ» — таймаут с экспоненциальной задержкой со средним 1/λ: `delays: { toB: rate(0.5) }`. Интенсивность — число или функция агента: `rate(({ context }) => context.speed)`.

- Задержка берётся из потока этой задержки (раздел 7) при входе в состояние.
- Интенсивность читается при входе. Если она меняется, пока агент в состоянии, новое значение действует со следующего входа.
- Интенсивность 0 — переход не срабатывает никогда (задержка `Infinity`). Отрицательная — ошибка.

### 4.3. По сообщению

`agent.send({ type: 'called', ...данные })` — сообщение в форме события XState.

- **Доставка — событие ядра в текущий момент** по правилам П-8: после событий, уже стоящих на этот момент. Внутри вызова `send()` агент не меняется; если агент шлёт сообщение сам себе, оно обработается после текущего шага.
- При доставке берутся переходы `on[тип]` текущего состояния, по порядку; срабатывает первый, чьё условие истинно.
- **Сообщение без подходящего перехода отбрасывается**: нет перехода для этого типа, ложны все условия, агент завершён или удалён. Оно не запоминается до следующего состояния (как в UML без отложенных событий, SCXML и XState) и считается в `population.discardedMessages` — чтобы ошибку модели было видно. Условия `always` после доставки проверяются всё равно (раздел 4.4), если агент не удалён.
- Данные сообщения доступны действиям и условиям как `event`.

### 4.4. По условию

`always: { guard: ({ context }) => context.x > 3, target: 'B' }` — переход без события; срабатывает, когда условие истинно в момент проверки.

**Когда проверяется условие** (решение П-22). Опроса по шагу времени нет. Условия текущего состояния проверяются:
1. сразу после входа в состояние, в том числе в начальное при создании;
2. после каждого события агента — сработавшего таймера или доставленного сообщения, даже если перехода по нему не было;
3. по явному вызову: `agent.check()` — один агент, `population.check()` — все агенты популяции в порядке столбцов (раздел 6). Проверка идёт сразу, внутри вызова; агенты, удалённые по ходу `population.check()`, пропускаются, добавленные — уже проверены при создании.

Поэтому условие, которое стало истинным из-за изменения **чужих** данных (другого агента, переменной модели, позже — системной динамики), агент заметит при своём следующем событии или при явной проверке. Кто меняет данные, от которых зависят условия, тот и вызывает `check()`. Если модели нужен опрос по шагу, его делает обычный процесс:

```ts
function* poll(): ProcessBody {
  for (;;) { yield timeout(1); customers.check(); }
}
```

Почему так: опрос по шагу — событие на каждого агента на каждом шаге; у 100 000 агентов это миллионы пустых событий, а момент срабатывания зависит от величины шага (переход «опаздывает» до шага). Проверка по событиям агента и по явному вызову точна по времени и ничего не стоит, пока ничего не происходит. Так же устроены переходы без события в SCXML и XState: они проверяются после каждого шага машины.

**Правила условий:**
- условие не должно менять модель: оно может вызываться много раз и в любом порядке проверок;
- переходы `always` пробуются по порядку, срабатывает первый с истинным условием; после него проверка повторяется уже в новом состоянии — так, пока ни одно условие не истинно (микрошаги SCXML), всё в тот же момент и без новых событий;
- больше 1 000 переходов без события подряд — ошибка: условия зациклились;
- переход `always` без условия должен вести в другое состояние: без цели или обратно в своё состояние он зациклился бы сразу, такое определение отклоняется.

`check()`, вызванный, пока этот же агент выполняет свой шаг (например, из его же действия), ничего не делает: условия всё равно проверяются в конце шага.

## 5. Порядок одновременных событий

**Между событиями** — правила ядра (П-8): время, приоритет, порядок постановки в очередь. Каждый таймер и каждое сообщение — отдельное событие с приоритетом 0. Отсюда:
- таймеры разных агентов, срабатывающие в один момент, идут в порядке их постановки, то есть в порядке входа агентов в состояния;
- таймер, который должен сработать в момент t, и сообщение, посланное в момент t: таймер поставлен раньше (при входе в состояние), поэтому срабатывает первым. Если он увёл агента из состояния, сообщение получит уже новое состояние;
- два таймера одного состояния с одинаковой задержкой: первым срабатывает тот, что раньше в `after` (в порядке ключей объекта в JavaScript: сначала целые числа по возрастанию, затем остальные ключи в порядке записи). Его переход выводит агента из состояния и отменяет второй таймер.

**Внутри события** (шаг агента): переход по событию, затем переходы `always` до устойчивого состояния (раздел 4.4). Всё в один момент модельного времени, новых событий нет. Сообщения, посланные из действий, — новые события после текущего.

**Синхронные вызовы:** `population.add()` и `check()` выполняют шаг агента сразу, внутри вызывающего кода. Если действие агента A вызывает `B.check()`, шаг B проходит внутри шага A.

**Метки событий в трассе** (параметр `trace` симуляции): `<популяция>#<номер агента>: <состояние> after <ключ>` для таймаута и `<популяция>#<номер агента>: message "<тип>"` для сообщения, например `customers#17: waiting after patience`. Метка считается только когда она нужна — для трассы или ошибки (решение П-29), поэтому без трассы строк на событие не создаётся. В Ф0-4 номера агента в метке не было: строка на каждое событие стоила около 20 % скорости.

## 6. Масштаб

Цель — сотни тысяч агентов (П-18). Поэтому:
- **без процессов-генераторов:** агент — объект с полями, а его таймеры и сообщения — события ядра своих видов, без объекта и замыкания на событие (ARCHITECTURE, «Очередь событий на массивах»). Таймаут несёт строку агента в столбцах и номер таймера, сообщение — строку таблицы сообщений популяции, где лежат агент и сообщение;
- **столбцы популяции** (П-30) — плотные типизированные массивы, строка на агента:
  - `ids` — номера агентов (`Float64Array`: номера не переполнятся);
  - номер состояния — `Uint16Array`, значение — номер в `statechart.stateNames`, до 65 535 состояний на диаграмму. Столбец — на каждую область диаграммы (`statechart.regionCount`); пока область одна, параллельные состояния добавят свои столбцы. Иерархическое состояние будет кодироваться номером листового состояния;
  - слоты ожидающих таймаутов — `Int32Array`, по ячейке на каждый таймер состояния (ширина — наибольшее число `after` в одном состоянии диаграммы); по ним таймауты отменяются при выходе из состояния и при удалении агента;
- `population.ids()` и `population.stateCodes(region)` отдают копии столбцов — готовый снимок для просмотра; передача во viewer — Ф0-6;
- **удаление уплотняет столбцы:** строку удалённого занимает последний агент, его таймауты переадресуются на новую строку (раздел 3). Дыр в столбцах нет, показ рисует их без отбора, а по `ids` узнаёт агентов после перестановок;
- **счётчики по состояниям:** `population.count('B')` — сколько агентов в состоянии сейчас, без перебора;
- **без потока случайных чисел на агента** (раздел 7).

**Замер** (`pnpm bench`, сводка job'а Benchmark): 100 000 и 1 000 000 агентов с двумя состояниями и переходами с интенсивностью 1. Цифры до и после Ф0-4б — в описании пулл-реквеста Ф0-4б и в DECISIONS (П-36); главное:
- память — 201 байт на агента при 100 000 и 187 при миллионе, вместе с ожидающим таймаутом (было 344 и 345);
- скорость в CI: 100 000 агентов — 23–27 единиц модельного времени в секунду (было 5,8–9,3 в зависимости от раннера, 6,51 в замере Ф0-4), миллион — 1,16–1,20 (было 0,29–0,41). На одной машине поочерёдно — ×2,9–3,3 и ×4,6;
- узкое место по-прежнему очередь: спуск по куче — цепочка зависимых промахов кэша, по одному на уровень. Дальше — «лестничная» очередь (П-28); раскладки кучи по строкам кэша и 8-арная куча на замере выигрыша не дали (П-34).

Ф0-4: популяция только росла, агент после Sink оставался в ней. Теперь его удаляют (`remove`); в Ф0-4в это будет делать Sink (П-31).

## 7. Случайность

Потоки (П-9, решение П-23) — по имени популяции:
- `agents/<популяция>` — для действий, условий и функции `context`;
- `agents/<популяция>/<имя задержки>` — для каждой именованной задержки-функции, в том числе `rate()`.

Почему не поток на агента: создание потока считает хэш имени через BigInt — замер 3,8 мкс и около 410 байт на поток. Для 100 000 агентов это 0,4 с и 41 МБ сверх самих агентов, для миллиона — 4 с и 410 МБ. Поток на задержку следует правилу блоков «свой поток на каждый источник случайности»: если поменять интенсивность одного перехода, числа других задержек не сдвинутся. Внутри одного потока числа достаются агентам в порядке их событий.

## 8. Агент как сущность

Агент можно провести через процессные блоки: у него есть `id` и `createdAt`, которые читают блоки. Source создаёт агентов фабрикой:

```ts
const door = new Source(sim, { name: 'door', interval: 1, entity: () => customers.add() });
door.connect(queue).connect(service).connect(sink);
```

- Агент идёт по блокам своим процессом, как любая сущность (`docs/BLOCKS.md`), и одновременно живёт по диаграмме: таймеры и сообщения не зависят от того, в каком он блоке.
- Фабрику Source вызывает только для прихода, который попал в следующий блок: потерянный приход агента не создаёт.
- `id` такой сущности — номер агента в популяции, `createdAt` — момент создания агента, то есть прихода.
- Блоки не знают об агентах и не шлют им сообщений. Сообщить агенту о шаге потока может код модели: например, свой `EntityReceiver` между блоками (так сделано в тесте «агент как сущность в очереди») или процесс модели. В Ф0-4в сущность станет агентом популяции, у блоков появятся действия при входе и выходе, а Sink будет удалять агента из популяции (П-31).

## 9. Ошибки

- **Определение** проверяется в `defineStatechart`: нет начального состояния, переход в несуществующее состояние, неизвестная задержка, неизвестный ключ, вложенные или параллельные состояния, условие не функция и т. п. — ошибка `INVALID_ARGUMENT` с указанием места (отрицательная задержка — `NEGATIVE_DELAY`).
- **Шаг агента:** если действие, условие, функция задержки или полей бросает исключение, задержка вышла отрицательной или условия зациклились — ошибка `AGENT_FAILED` с именем агента (`customers#17`), моментом времени, состоянием и исходной ошибкой в `cause`.
- **Вызовы:** сообщение без строкового `type`, неизвестное имя состояния в `count()`, несуществующая область в `stateCodes()`, удаление не агента или агента чужой популяции, повторное имя популяции — `INVALID_ARGUMENT`.

## 10. Проверка

Тесты в `packages/kernel/src/agents` и `packages/blocks`:
- **моменты переходов:** таймаут, интенсивность (задержки совпадают с числами потока задержки), сообщение, условие (при входе, после события, по `check()`, без опроса), отмена таймаута при выходе, `reenter`, одновременные события, конечное состояние, отброшенные сообщения;
- **удаление:** уплотнение столбцов и `ids`, таймауты удалённого не срабатывают, а таймауты переставленного агента срабатывают для него, сообщения удалённому отбрасываются и считаются, удаление себя из своего действия, удаление по ходу `population.check()`, метки после перестановки;
- **повторяемость:** одинаковый seed — одинаковая трасса событий, в том числе с удалением и добавлением агентов; трасса модели-эпидемии совпадает событие в событие (с номерами) с трассой ядра Ф0-4;
- **агент как сущность в очереди:** Source создаёт агентов, они ждут в Queue, становятся «нетерпеливыми» по таймауту, получают сообщение, когда их вызывают на обслуживание, и выходят через Sink;
- **аналитическая проверка:** N независимых агентов с двумя состояниями A и B, переходы A→B с интенсивностью a и B→A с интенсивностью b (марковская цепь с двумя состояниями, Ross, гл. 6):
  - доля агентов в B в установившемся режиме — a / (a + b);
  - среднее время в A — 1/a, в B — 1/b;
  - цепь забывает начало как exp(−(a + b)·t), поэтому разгон — 13 / (a + b) (остаток e⁻¹³);
  - метод — повторы с отбрасыванием разгона, как у блоков (П-16): 20 повторов со своими потоками, t-интервал уровня 99,9 %, полуширина не больше 10 % значения;
  - время в состоянии меряется по пребываниям, начавшимся в окне наблюдения, и каждое досматривается до конца; так в выборку не попадает пребывание, которое уже шло в начале окна и в среднем вдвое длиннее (парадокс инспекции).
- **замер** (`pnpm bench`, job Benchmark): 100 000 и 1 000 000 агентов с двумя состояниями — единиц модельного времени и событий в секунду, память на агента и цифры ядра до Ф0-4б для сравнения (П-36).
