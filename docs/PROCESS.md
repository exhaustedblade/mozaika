# Как ведём разработку

Главное правило: **память проекта — репозиторий, а не история чата.** Длинные сессии теряют детали при сжатии контекста (опыт Architect: одна сессия разрасталась больше гигабайта). Поэтому каждая сессия коротка и опирается на документы и тесты.

## 1. Репозиторий — центр всего

- **GitHub-репозиторий** создаёт владелец (от своего имени). Открыт с 21.10.2026 (Фаза 0), чтобы превью на GitHub Pages работало без платного тарифа (П-6); раньше план был открыть при версии 0.1.
- `CLAUDE.md` — правила проекта; ИИ читает его в начале каждой сессии.
- `docs/` — план, архитектура, решения, правила «чистой комнаты», этот процесс.
- **Задачи** — GitHub Issues и доска Projects. Одна фича — одна карточка с критерием «готово».
- **Журнал решений** — `docs/DECISIONS.md`: что решили, когда и почему.
- **CHANGELOG.md** (появится с первым релизом) — что изменилось в каждой версии.

## 2. Одна сессия — одна задача

**Начало сессии:**
1. Прочитать `CLAUDE.md`, задачу (issue) и нужные разделы `docs/`.
2. Сказать в двух-трёх строках, что будет сделано и как проверим.

**Работа:**
3. Отдельная ветка (или worktree) на задачу.
4. Сначала тест (что должно получиться), потом код.
5. Все проверки локально зелёные.

**Конец сессии:**
6. Коммит и пулл-реквест: что сделано, как проверено, ссылка на превью, скриншоты.
7. Обновить документы, если изменилось решение или архитектура.
8. Короткий итог владельцу: сделано / проверено / что решить.

**Мерджит владелец.** Задачи, которые не помещаются в одну сессию, делятся на несколько карточек.

## 3. Автоматические проверки (GitHub Actions на каждый пулл-реквест)

| Проверка | Зачем |
|---|---|
| Типы (TypeScript strict) и линтер | грубые ошибки |
| Юнит-тесты ядра | события, часы, порядок одновременных событий, seed |
| Тесты блоков против теории очередей | M/M/1, M/M/c, закон Литтла — точные формулы |
| Законы моделей (самопроверка) | балансы, границы, монотонность, сложение сценариев |
| Мутационная проверка законов (периодически) | законы действительно ловят ошибки |
| Регрессия демо-моделей | результаты эталонных моделей не «уплывают» |
| Замер скорости | события в секунду, время прогона не ухудшается |
| Скриншоты сцены через Playwright | «глаза»: сцена рисуется, ничего не поехало |
| Сборка и превью по ссылке (GitHub Pages / preview) | владелец открывает и кликает без установки |

**Правило:** «готово» — это когда все проверки зелёные и владелец посмотрел превью, а не когда ИИ сказал «работает».

## 4. Роли

- **Владелец продукта (exhaustedblade):**
  - ставит и приоритизирует задачи; ИИ-разработчик берёт в работу только их (задачи и пулл-реквесты от других людей показывает владельцу);
  - смотрит превью, говорит «нравится / нет»;
  - принимает решения из журнала;
  - мерджит;
  - отвечает за юриста, сообщество и деньги.
- **ИИ-разработчик (Claude Code):** код, тесты, документация, отчёты, предложения решений с вариантами.
- **Ревьюер:** отдельный ИИ-агент — только на крупные пулл-реквесты и перед релизами.

**Еженедельный итог** (10 минут): что сделано, что дальше, какие решения нужны.

## 5. Помощники — точечно

Агенты и workflow — только там, где действительно нужны.

- агент-ревьюер на крупные изменения;
- ночная регрессия по расписанию с отчётом;
- облачные сессии для длинных задач, чтобы не занимать компьютер владельца;
- параллельные задачи — в отдельных ветках или worktree, не больше двух-трёх одновременно.

## 6. Внешние сервисы

**На старте:** GitHub (репозиторий, Issues, Projects, Actions, Pages, Releases), Vitest, Playwright, хуки «перед коммитом прогнать тесты». Больше ничего.

**n8n** — не для разработки (это делает GitHub Actions). Может пригодиться позже:
- **рутина:** CI упал / вышел релиз / пришла заявка → Telegram, карточка в задачах, пост в канал;
- **цифровые двойники:** подтягивать живые данные (API, таблицы, датчики) в модель по расписанию.

Лицензия n8n — fair-code (Sustainable Use License), не открытая в строгом смысле. Как внешний инструмент — можно, встраивать в продукт — только после проверки.

Новый сервис подключаем, когда есть настоящая потребность, и записываем в журнал решений.

## 7. Новая зависимость

Перед добавлением любой библиотеки:
1. проверить лицензию (совместима с Apache-2.0 / open core);
2. проверить, что проект живой (релизы, поддержка);
3. записать в таблицу компонентов `docs/PLAN.md` с лицензией и датой проверки.
